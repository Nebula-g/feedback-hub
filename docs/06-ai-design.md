# 06 · AI 模块设计说明（挑战赛道）

> 本文件回答四个问题：**AI 在哪儿起作用、它到底产出什么、人怎么盖棺定论、它挂了怎么办**。

---

## 一、先立规矩：本项目的三条红线

| 编号 | 红线                                               | 代码层如何保证                                                                                 |
| -- | ------------------------------------------------ | -------------------------------------------------------------------------------------- |
| A1 | **AI 的产出只是草稿，不构成业务事实**                          | AI 结果只写入 `ai_candidate_issue`；`issue / feedback / improvement_task` 三张正表由人工动作驱动        |
| A2 | **必须有人确认，且确认过程可回查**                              | 只有 `POST /api/ai/candidates/{id}/confirm` 能生成 issue，且强制记录 `confirmed_by` + `confirm_time` |
| A3 | **AI 不得决定优先级**                                   | `AiCandidateSuggestion` 数据结构里**没有** priority 字段；`ai_suggested_priority` 全系统不存在         |
| A4 | **信息不足时禁止臆造**                                     | Prompt 明确要求返回 `INSUFFICIENT_EVIDENCE`；规则实现内置长度阈值兜底                                  |
| A5 | **原始反馈不可被 AI 修改**                                  | `feedback` 表只有"新增"接口，没有任何修改正文的接口                                                       |
| A6 | **每次调用必须留证**                                      | `ai_generation_log` 无论成功失败一律落库（输入快照 / 返回原文 / 耗时 / 状态）                            |
| A7 | **AI 不可用 ≠ 业务中断**                                | 双实现 + 自动降级；前端 503 不阻断，引导手工继续                                                        |

**一句话概括**：AI 负责"把 60 条口语化抱怨整理成 9 张卡片"，PM 负责"这 9 张卡片哪些成立、怎么改、什么优先级"。前者可以重跑无数次，后者一旦落库就是事实。

## 二、AI 的三个作用点

```
   原始反馈（只读）
        │
        │  ① EXTRACT  单条提取：一段话 → 结构化的【现象 / 诉求 / 模块】
        ▼             一条反馈可能拆出多个 item（"而且 / 另外…"）
   结构化条目
        │
        │  ② CLUSTER  聚类：同模块内按【问题现象】归并 → 候选卡片
        ▼
   AI 候选卡片（草稿，状态 DRAFT）
        │
        │  ③ DRAFT    起草：为已确认问题生成需求说明与验收条件
        ▼
   需求草稿（只返回不落正式字段）
```

| 作用点      | 枚举值       | 触发时机              | 落库日志 `biz_type` |
| -------- | --------- | ----------------- | --------------- |
| 单条提取     | `EXTRACT` | 聚类前的第一遍处理         | `EXTRACT`       |
| 聚类成卡片    | `CLUSTER` | PM 点击「生成候选问题」     | `CLUSTER`       |
| 起草需求     | `DRAFT`   | PM 在问题详情点击「AI 起草」 | `DRAFT`         |

> `EXTRACT` 是 `CLUSTER` 的内部第一遍；对外只在「生成候选卡片」这一个入口触发，
> 因此演示时日志里最常见的是 `CLUSTER` 与 `DRAFT` 两类。

## 三、双实现与降级

```
            ┌─ 可用 ─▶ LlmAiServiceImpl（真实大模型，OpenAI 兼容协议）
 choose() ──┤
            └─ 不可用 / 调用失败 ─▶ RuleAiServiceImpl（关键词 + 模板，零依赖）
```

**判定顺序**（`AiCandidateServiceImpl.chooseService()`）：

1. `ai.provider=llm` **或** `ai.fallback.simulate-failure=true` → 选大模型实现；
2. 否则直接选规则实现。

**降级触发条件**（两条同时满足）：

1. `ai.fallback.enabled=true`
2. 当前用的不是规则实现（否则没得降）

**日志状态判定**：

| 情况                       | `status`   | `provider` | `error_msg` |
| ------------------------ | ---------- | ---------- | ----------- |
| 大模型直接成功                  | `SUCCESS`  | `LLM`      | null        |
| 大模型失败 → 规则兜底成功           | `FALLBACK` | `RULE`     | 首选失败原因      |
| 规则兜底也失败 / 未启用降级          | `FAILED`   | —          | 失败原因        |
| 大模型调用超时（HTTP 408/504 或超时） | `TIMEOUT`  | —          | 超时说明        |

**演示开关**：

```yaml
ai:
  provider: ${AI_PROVIDER:rule}                  # 环境变量可覆盖
  fallback:
    enabled: true
    simulate-failure: ${AI_SIMULATE_FAILURE:false}
```

现场演示降级，任选其一：

- 直接改 `application.yml` 里 `simulate-failure: true` 后重启；
- 或启动前设置环境变量 `AI_SIMULATE_FAILURE=true`。

> 注意：即便 `provider=rule`，只要 `simulate-failure=true`，
> 系统也会先走一次大模型调用（必然失败）再降级，
> 从而在调用记录里完整复现「失败 → 降级」的全过程。

## 四、Prompt 设计

### 4.1 五条设计原则

1. **强制 JSON**：给出 schema，禁止任何额外文字、解释或代码块标记；
2. **禁止臆造**：信息不足时返回 `INSUFFICIENT_EVIDENCE`，不允许猜测模块或现象；
3. **现象优先**：相似度判断基于「问题现象」而非「关键词重合」——
   这是为了处理"发票传不上去"与"发票上传成功但查不到"这类**关键词相似但现象不同**的陷阱；
4. **可回溯**：每次输出必须给出所依据的 `feedback_id` 列表；
5. **不输出优先级**：Prompt 中明令禁止，数据结构里也没有对应字段。

### 4.2 EXTRACT 系统提示词

```text
你是一个企业报销软件的用户反馈分析助手，负责把客服录入的口语化反馈整理成结构化信息。

严格要求：
1. 只输出 JSON，不要输出任何解释、标题或代码块标记。
2. 判断"是否属于同一件事"必须依据【问题现象】是否相同，而不是文字里是否出现了相同的词。
   例如"发票传不上去"与"发票上传成功但查不到"，虽然都含"上传"，但现象不同，是两个问题。
3. 如果用户的话里出现并列（如"而且""另外""同时"），说明他在说多件事，必须拆成多个 item。
4. 如果用户说得太笼统，无法判断具体哪里出问题（例如"有问题""系统很卡""希望能改进一下"），
   不要猜测，直接返回 {"insufficient": true}。
5. 严禁输出优先级、严重程度或排期建议。

输出 schema：
{"insufficient": false, "items": [{"module": "模块代码", "phenomenon": "现象", "userDemand": "诉求", "signature": "现象签名"}]}
```

### 4.3 CLUSTER 系统提示词

```text
你是一个企业报销软件的用户反馈分析助手，负责把一批用户反馈归纳成候选问题卡片。

严格要求：
1. 只输出 JSON，不要输出任何解释、标题或代码块标记。
2. 只有当多条反馈描述的【问题现象】相同时，才归入同一张卡片；
   仅关键词相似但现象不同，必须拆成不同卡片。
3. 一张卡片必须给出它所依据的 feedback_id 列表，不得凭空生成。
4. 不得合并属于不同功能模块的反馈。
5. 对于描述过于笼统、无法判断现象的反馈，把它的 id 放进
   insufficientFeedbackIds，不要为它生成卡片，更不要臆测。
6. 严禁输出优先级、严重程度或排期建议；confidence 只表示你对"这些反馈是同一件事"的确信程度。

输出 schema：
{"candidates": [{"title": "标题", "phenomenon": "现象", "userDemand": "诉求",
                 "module": "模块代码", "confidence": 0.86, "reason": "归类理由",
                 "feedbackIds": [1,2,3]}],
 "insufficientFeedbackIds": [58]}
```

### 4.4 DRAFT 系统提示词

```text
你是一个企业报销软件的产品经理助手，负责为已确认的问题起草需求说明与验收条件。

严格要求：
1. 只输出 JSON，不要输出任何解释、标题或代码块标记。
2. 只能基于给定的问题信息与用户原始反馈起草，不得编造未提及的功能或数据。
3. 验收条件必须是可验证的具体条目，避免"体验更好""更流畅"这类无法衡量的描述。
4. 严禁输出优先级、严重程度或排期建议。
5. 草稿中如存在需要人工确认的点，请显式写在"待确认事项"小节里。

输出 schema：
{"draftContent": "Markdown 格式的需求说明",
 "acceptanceCriteria": "编号列出的验收条件"}
```

### 4.5 关键设计点说明

| 设计点                    | 为什么这么写                                                                         |
| ---------------------- | ------------------------------------------------------------------------------ |
| 反复强调"只输出 JSON"         | 大模型在 system 提示较长时容易在 JSON 前后加寒暄。即便如此，解析端仍会剥离 ```json 代码块并截取 `{...}`，双保险        |
| 显式举出"关键词相似但现象不同"的反例    | 只说"要判断语义相似"太抽象，模型仍会按关键词聚类。给出具体反例后误合并率明显下降                               |
| `"insufficient": true` 专用出口 | 与其让模型"尽量猜"，不如给它一条体面的退路。这样"说不清楚"的反馈会被单独隔离，而不是被硬塞进某个卡片                        |
| 要求输出 `feedbackId` 列表   | 这是"可回查"的落点。没有它，PM 无法验证 AI 是不是在凭空归纳                                          |
| 温度 0.2                 | 归纳任务要的是稳定复现，不是创意。同一批输入两次跑出不同卡片，PM 会失去信任                                      |
| 解析失败即降级                  | 不让脏数据进入业务表。解析不了的返回，其原文照样入库留证                                                 |

## 五、规则实现（兜底地板）

### 5.1 三步走

```
   ① 按并列连词切分   而且 / 并且 / 另外 / 还有 / 同时 / 以及
      └─ 不按逗号切：中文口语里逗号常只是停顿，
         "传不上去，换了三个网络都不行"说的是同一件事
   ② 子句匹配现象规则表（有序，先命中优先）
      └─ 第一轮只在本模块规则里找，第二轮才跨模块找
         （这样"上传失败+退回原因"能被拆成两个模块的问题）
   ③ 按「模块 + 现象签名」归并
      └─ 依据不足 / 未命中的，一条反馈一张卡，绝不归并
```

### 5.2 现象规则表（节选 · 发票上传模块）

| 签名                    | 命中关键词                                                                        | 归纳标题                      |
| --------------------- | ---------------------------------------------------------------------------- | ------------------------- |
| `IU_OCR_WRONG`        | OCR / 识别不出 / 识别出来 / 识别不准                                                      | OCR 识别结果与票面不一致            |
| `IU_RECOGNIZE_SLOW`   | 识别中 / 一直显示                                                                   | 识别状态长时间停留在「识别中」           |
| `IU_NOT_VISIBLE`      | 上传成功但 / 看不到这张发票 / 查不到                                                        | 上传成功但在报销单中查不到             |
| `IU_FORMAT_ERROR`     | 格式错误 / 格式不支持 / 文件类型                                                           | 格式校验误报，合法 PDF 被拒绝        |
| `IU_CANNOT_DELETE`    | 删掉 / 删除按钮 / 删不了                                                               | 已上传发票无法删除后重传              |
| `IU_CANNOT_MOVE`      | 选错了 / 移动                                                                      | 发票上传错报销单后无法移动             |
| `IU_DUPLICATE`       | 重复                                                                            | 重复上传同一张发票无提示              |
| `IU_UPLOAD_FAIL`      | 传不上去 / 上传失败 / 传不了 / 都失败 / 总是失败 / 还是失败 / 中途失败 / 只成功 / 卡在 / 超时 / 没反应 / 网络错误 | 上传失败且缺少明确失败原因            |

> 完整规则表见 `RuleAiServiceImpl.RULES`，共约 30 条，覆盖四个业务模块。

### 5.3 置信度计算口径（公开、可复算）

```
base                = 0.50
+ 命中已知规则        = 0.15
+ 关联反馈增量        = min(0.30, (条数 - 1) × 0.10)
- 依据不足           = 0.25
- 未命中规则          = 0.10
最终截断到 [0.05, 0.95]
```

**置信度不触发任何自动动作**。即便 0.95 也仍需 PM 手动点击确认——它唯一的用途是列表排序与提示 PM 优先看哪些卡片。

## 六、日志与证据链

每次调用（无论成功失败）写入一条 `ai_generation_log`：

| 字段               | 作用                       |
| ---------------- | ------------------------ |
| `input_snapshot` | 本次喂给 AI 的每一条反馈 id 与原文    |
| `output_raw`     | AI 返回原文，未做任何加工           |
| `provider`       | 实际用的是 LLM 还是 RULE        |
| `model`          | 模型名；规则实现固定写 `rule-engine-v1` |
| `status`         | SUCCESS / FAILED / TIMEOUT / FALLBACK |
| `error_msg`      | 失败原因                     |
| `cost_ms`        | 耗时                       |
| `operator_id`    | 谁点的                      |

**为什么失败日志也要留**：它证明系统确实尝试过、确实失败了、也确实降级了。
只记录成功的日志，等于把降级这件事藏起来，反而更不可信。

**本表为追加写（append-only）**：Service 层只提供 insert，不提供任何 update/delete 入口，
且**不设逻辑删除字段**——删除日志会破坏证据链完整性。这一点与业务表策略相反，是刻意区分的。

| ③ 关键词相似但现象不同      | FB-0009「发票传不上去」 vs FB-0010「上传显示成功但查不到」         | 生成 **2 张独立卡片**，未合并                                                      |

| ⑧ 驳回必填理由           | 驳回时不填原因                                         | 返回 **400**                                                               |

## 八、诚实交代：规则实现的局限

规则实现是**地板不是天花板**，它有几个明确的短板，答辩时应如实说明：

1. **认不出同义改写**：只匹配关键词，"无法提交发票" 和 "传不上去" 在规则眼里是两件事；
2. **规则表需要人工维护**：新增一类问题要加一条规则，无法自动发现新问题；
3. **不理解否定与转折**："上传成功但查不到" 这类含转折句依赖关键词兜底，容易误判；
4. **置信度是启发式的**：不是概率校准结果，只适合排序参考。

**这正是分层设计的意义**：把"一定能跑通、但不够聪明"的规则放在最底层，
把"聪明但不保证可用"的大模型放在上层，中间用一条明确的降级链路连起来。
任何一层出问题，系统都还有下一层接着，业务不会掉在地上。

**后续可改进方向**：

- 引入文本向量（embedding）做语义相似度，替代纯关键词匹配；
- 规则表配置化，支持 PM 在界面上维护关键词；
- 对 LLM 输出做二次校验（反馈 ID 是否存在、模块是否合法），不合法则拒绝入库。
