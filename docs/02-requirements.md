## 1. 项目问题

### 1.1 具体场景

> **周三上午 9:30**，某报销软件公司的产品经理小张打开客服系统，发现过去一周累积了 **60 条**用户反馈。
>
> 他逐条阅读，发现了这些：
> - 有 7 条在说同一件事，但说法完全不同：*"发票死活传不上去"*、*"上传发票提示格式错误"*、*"附件传了三次都失败"*……
> - 有 1 条反馈里其实藏了两个问题：*"上传发票总是失败，而且报销单被退回后也找不到原因"*
> - 有一条只写了 *"审批太麻烦"* 五个字，看不出具体哪里麻烦
> - 有一条是客户在电话里情绪激动地抱怨，措辞激烈但其实影响很小
>
> 中午之前他必须给出一份「本周值得改的问题清单」交给研发。
>
> **结果**：他凭印象合并了 7 条发票反馈，漏掉了那条藏在长句里的第二个问题，
> 又因为那条情绪激烈的投诉把一个小问题提到了 P0。
> 一周后客户追问"上次说的找不到退回原因的问题改了吗"，他翻遍聊天记录也找不到出处。

### 1.2 问题描述

| 项目 | 内容 |
| --- | --- |
| **谁在做** | 客服人员记录反馈、产品经理归并并决定改进项、开发测试执行 |
| **遇到什么问题** | 反馈归并与优先级判断完全依赖个人经验和注意力；原始反馈与最终任务之间没有关联记录 |
| **造成什么后果** | 重复问题被低估、不同问题被误并、优先级被情绪带偏、决策无法回查 |
| **系统帮助谁** | 主要帮助**产品经理**，其次帮助**客服**（录入规范化）和**开发测试**（任务可追溯） |

### 1.3 系统不做什么

**系统不自动决定产品该做什么。** 它只完成第一轮整理（AI 归纳），
把判断权和责任留给产品经理，并保证每一步都能回到原始反馈。

## 3. 完整流程

### 3.1 主流程（正常路径）

```text
① 客服录入/批量导入脱敏反馈
        ↓  feedback.status = NEW
② AI 提取单条反馈的：涉及模块 / 问题现象 / 用户诉求
        ↓  写入 ai_generation_log（SUCCESS）
③ PM 点击「生成候选问题」
        ↓  按模块硬分组 → 组内 AI 语义聚类
        ↓  生成 ai_candidate_issue（status = DRAFT）
        ↓  关联 feedback_issue_link
④ PM 查看候选卡片 + 原文依据
        ↓  确认 / 修改后确认 / 合并到已有问题 / 驳回
        ↓  ai_candidate_issue.status = CONFIRMED / MODIFIED / MERGED / REJECTED
        ↓  确认类操作生成正式 issue
⑤ AI 为已确认问题生成需求说明 + 验收条件（草稿）
        ↓  存入 issue.ai_draft_content
⑥ PM 修改草稿 → 建立改进任务
        ↓  issue.final_content（PM 定稿）
        ↓  improvement_task（含 PM 手选的 priority）
⑦ DEV 推进状态：待开发 → 开发中 → 待验证 → 已完成
        ↓  每次变更写入 task_event
⑧ 完成：全过程时间线可查询
```

### 3.2 异常流程

| # | 异常情况 | 处理方式 |
| ---: | --- | --- |
| E1 | 反馈内容无意义（如"有问题，找你们技术"） | AI 返回 `INSUFFICIENT_EVIDENCE`，卡片标记「信息不足」，等待客服补充；**AI 不得臆造细节** |
| E2 | 一条反馈含多个问题 | 拆分为多张候选卡片，同一 `feedback_id` 出现在多条 link 中 |
| E3 | 两条反馈关键词相似但现象不同 | **不自动合并**，生成独立卡片并在 AI 输出中给出"建议人工判断"提示 |
| E4 | **AI 服务不可用 / 超时** | 捕获异常 → 写 `ai_generation_log(FAILED)` → 页面提示"已切换手工模式" → PM 手工创建问题与需求，业务流程完整走完 |
| E5 | PM 驳回候选卡片 | `status = REJECTED`，关联的 feedback 回到 NEW 状态可重新归类；**卡片不可逆转回 DRAFT** |
| E6 | 验证不通过 | `PENDING_VERIFY → IN_PROGRESS`，**必须填写打回原因** |
| E7 | 两人同时确认同一张候选卡片 | 乐观锁（version 字段）拦截，后提交者收到"数据已被修改，请刷新" |
| E8 | 越权操作 | 返回 403，页面提示"无权限执行此操作" |

## 4. 关键规则

### 4.1 状态流转规则

**① 反馈 `feedback.status`**
```
NEW（未归类）→ LINKED（已关联问题）→ CLOSED（随任务完成）
             ↘ IGNORED（PM 判为无效）
```
- ❌ `LINKED → NEW`：需 PM 解除关联，且必须留记录
- ❌ `CLOSED → 任何状态`：终态不可逆

**② 候选卡片 `ai_candidate_issue.status`**
```
DRAFT → CONFIRMED（直接确认）  ┐
      → MODIFIED（修改后确认） ├→ 生成正式 issue
      → MERGED（并入已有问题） ┘
      → REJECTED（驳回）
```
- ❌ `REJECTED → CONFIRMED`：必须重新生成候选
- ❌ `CONFIRMED / MERGED → DRAFT`：不可逆

**③ 改进任务 `improvement_task.status`**
```
TODO → IN_PROGRESS → PENDING_VERIFY → DONE
  └──────────────→ WONT_DO（PM 决定不做）
```
- ❌ `TODO → DONE`：必须走完全流程
- ❌ `TODO → PENDING_VERIFY`：不得跳过"开发中"
- ❌ `DONE → 任何业务状态`：如需重开，由 PM 新建任务并关联原 issue
- ⚠️ `PENDING_VERIFY → IN_PROGRESS`：允许（验证不通过打回），**必须填原因**

### 4.2 权限规则

| 规则 | 说明 |
| --- | --- |
| R1 | 只有 **PM** 可以设定和修改任务优先级 |
| R2 | 只有 **DEV** 可以推进任务状态（PM 只能创建和关闭） |
| R3 | 任何角色都**不能删除或修改原始反馈内容** |
| R4 | 客服只能查看自己录入的反馈明细；PM/DEV 可查看业务范围内全部 |
| R5 | 任务负责人只能操作分配给自己的任务 |

### 4.3 AI 业务约束（挑战赛道硬性要求）

| # | 约束 |
| ---: | --- |
| A1 | AI 只能处理系统中已录入的**脱敏**反馈 |
| A2 | AI **不能**把含义不同的反馈仅因关键词相同而强行合并 |
| A3 | 每张候选卡片**必须能回到原始反馈**（关联 `feedback_id`） |
| A4 | AI **不能**根据表达情绪自动决定优先级 |
| A5 | AI 生成的需求与验收条件**只是草稿**，必须经 PM 确认 |
| A6 | AI **不能修改或删除**原始反馈 |
| A7 | 模型不可用时，PM 仍可手工完成分类与任务创建 |

## 5. 第一版范围

### 5.1 必须完成

| # | 内容 |
| ---: | --- |
| 1 | 单条录入与批量导入脱敏反馈（含图片凭证，走存储抽象层） |
| 2 | 反馈分类：报销单填写 / 发票上传 / 审批进度 / 退回修改 / 其他 |
| 3 | AI 生成候选问题卡片，并关联原始反馈 |
| 4 | PM 确认、修改、合并、驳回候选卡片 |
| 5 | AI 为已确认问题生成需求说明与验收条件草稿 |
| 6 | PM 修改草稿并建立改进任务（含自定优先级） |
| 7 | DEV 更新任务状态：待开发 / 开发中 / 待验证 / 已完成 |
| 8 | 从原始反馈到改进任务与验证结果的完整时间线 |
| 9 | JWT 登录与四类角色的权限控制 |
| 10 | Nginx 前后端分离部署 |

### 5.2 明确不做

- ❌ 真实报销审批、资金支付、发票真伪校验
- ❌ 接入真实企业报销系统或客服工单系统
- ❌ 保存真实姓名、手机号、金额、单位、发票图片
- ❌ 爬取第三方平台评论数据
- ❌ AI 自动决定开发优先级、发布时间、人员绩效
- ❌ 真实邮件/短信发送

### 5.3 扩展功能（上限 1 项，最后做）

**反馈检索与相似回查**：输入一句自然语言，检索历史相似反馈及其最终处理结论。
与核心考点（原文可回查、AI 有依据）强相关，成本低于统计看板。

## 8. AI 使用说明（挑战赛道额外要求）

### 8.1 AI 使用什么材料（输入）

**仅限系统内已录入的脱敏反馈数据**，具体包括：

- 反馈正文（脱敏后）
- 客服标注的功能模块
- 反馈来源渠道
- 客户标签（脱敏编号，如 `C-0017`）
- 关联的问题与处理记录

**不包含**：任何真实姓名、手机号、身份证、金额、单位名称、发票原件。

### 8.2 AI 生成什么内容（输出）

| # | 输出物 | 性质 |
| ---: | --- | --- |
| 1 | 涉及功能模块、问题现象、用户诉求的结构化提取结果 | **草稿** |
| 2 | 候选问题卡片（含关联反馈 ID 列表、置信度） | **草稿** |
| 3 | 需求说明草稿 + 验收条件草稿 | **草稿** |
| 4 | 客观统计依据（关联反馈条数、影响客户数、涉及模块） | 参考信息 |

### 8.3 由谁确认

| 输出物 | 确认人 | 确认动作 |
| --- | --- | --- |
| 结构化提取结果 | 客服（可修正模块标注） | 编辑保存 |
| 候选问题卡片 | **产品经理** | 确认 / 修改后确认 / 合并 / 驳回 |
| 需求与验收条件草稿 | **产品经理** | 修改后建立改进任务 |
| 优先级 | **产品经理**（唯一） | 手选 P0 / P1 / P2 |

### 8.4 AI 无法处理时如何改由人工继续

```
① AI 调用失败 / 超时 / 返回非法格式
        ↓
② 捕获异常，写入 ai_generation_log（status = FAILED，记录 error_msg）
        ↓
③ 页面显示："AI 服务暂不可用，已切换为手工模式"
        ↓
④ PM 手工完成：
   - 手工创建问题（填写标题、描述、模块）
   - 手工关联原始反馈（多选）
   - 手工填写需求说明与验收条件
   - 手工设定优先级
        ↓
⑤ 后续流程与 AI 路径完全一致，无任何功能缺失
```

**可验证性**：所有失败均落库，答辩时可现场演示「AI 失败 → 手工完成」的完整链路。
