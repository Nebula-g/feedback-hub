## 二、接口契约三方核对

### 2.1 为什么需要做这件事

前后端分离项目最容易出现、也最难靠肉眼发现的一类缺陷是：
**前端引用了后端根本不返回的字段**。

这类错误的特点是：
- 编译能过（前端是弱类型，字段名写错不报错）
- 接口能通（HTTP 200，响应正常返回）
- 只有点开页面才看得出"这一块是空白"

在本项目阶段 4 联调时，已经靠肉眼发现过 2 次（`AiLogView` 引用了不存在的
`errorMessage`/`promptText`/`responseText`、业务类型选项写成了
`CANDIDATE_ISSUE`/`REQUIREMENT_DRAFT`）。
靠人工逐个页面核对 30 个接口、上百个字段既不现实也不可靠，
因此编写了 `contract_check.py` 做自动化差集比对。

### 2.2 核对方法

```
【1】接口清单：解析后端 @XxxMapping 注解  ↔  解析前端 api/*.js 的 request 调用
【2】响应字段：运行时拉取真实 JSON 字段   ↔  扫描 .vue 中 row./detail./task. 等引用
【3】请求字段：前端提交的键               ↔  后端 DTO 声明的字段
【4】枚举值  ：后端枚举 code              ↔  前端下拉选项 value
```

### 2.3 核对结果

**【1】接口清单**：后端声明 30 个，前端调用 29 个，无缺失、无多余。
唯一未调用的是 `GET /api/ai/status`（ADMIN 运维接口，前端无页面，属有意设计）。

**【2】响应字段**：8 个主要页面的字段引用全部有后端来源。

**【3】请求字段**：10 个主要 DTO 的提交字段均被后端接收。

**【4】枚举值**：前端 32 个选项值全部能在后端 11 个枚举中找到。

## 三、业务与权限 Review：发现并修复的 4 处缺陷

Review 不是"看一遍代码"，而是逐条对照设计意图检查实现是否真的落地。
以下是本次 Review 发现的 4 处**真实缺陷**（均已修复）。

### 缺陷 1：`TaskVO.issueNo` 声明了却从未赋值（静默空白）

**现象**：`TaskVO` 里声明了 `issueNo` 字段，前端任务详情也用
`task.issueNo` 回显"本任务来自哪个问题"，但后端 `toVO()` 的
builder 链里**从来没有给它赋过值**。

**为什么危险**：接口返回 200、前端不报错、后端不报错，
用户只会看到页面上这一栏永远是空的。
这类"静默缺失"比直接报错更难发现。

**修复**：批量查询 issue 编号后回填（沿用已有的批量查询模式，避免 N+1）：

```java
// 修复：此前该字段声明了却从未赋值，前端会一直显示空白
.issueNo(entity.getIssueId() == null
        ? null : issueNos.get(entity.getIssueId()))
```

> 这个缺陷正是靠自动化契约核对发现的 —— 脚本会检查
> "VO 声明的字段是否真的在 builder 里被赋过值"。

---

### 缺陷 2：`sourceType` 枚举语义散落成字符串常量

**现象**：issue 的来源类型 `AI` / `MANUAL` 是枚举语义，
但后端只是写在 `IssueServiceImpl` 里的两行
`private static final String`，前端则在页面里硬编码同样的字符串。

**问题**：
1. 没有单一事实来源，任一侧拼错都不会报错，只会静默产生脏数据；
2. 前端选项值无法与后端字典自动核对。

**修复**：抽取 `IssueSourceType` 枚举（写法与既有的 `LinkType` 保持一致），
并在查询条件处做枚举归一化，保证查询值永远合法：

```java
.eq(StringUtils.hasText(query.getSourceType()),
        Issue::getSourceType,
        IssueSourceType.of(query.getSourceType()).getCode())
```

---

### 缺陷 3：PM 无法关闭任务（权限被双重拦截，分支成死代码）★ 最典型

**现象**：状态机设计里明确写了 `WONT_DO` =「已关闭：**PM 决定不做**」，
`TaskServiceImpl` 里也确实写了这段校验：

```java
if (TaskStatus.WONT_DO == target) {
    // 关闭任务属于产品决策，仅 PM 可执行
    if (!isAdmin && !RoleEnum.PM.getCode().equals(role)) {
        throw new BizException(ResultCode.FORBIDDEN, "只有产品经理可以关闭任务");
    }
}
```

但 Controller 上的注解是：

```java
@PreAuthorize("hasRole('DEV')")   // ← PM 在这里就被 403 挡掉了
@PutMapping("/{id}/status")
```

**结果**：PM 永远走不到 Service 里的那一段，
「PM 决定不做」这条状态机出口**实际上完全不可用**，
而 Service 里的 PM 分支成了永远执行不到的死代码。
前端也写死了 `canTransit = role === 'DEV'`，PM 连按钮都看不到。

**修复**：注解放宽为 `hasAnyRole('DEV', 'PM')`，
由 Service 内部的角色分支做精确约束：
- DEV：推进开发状态（IN_PROGRESS / PENDING_VERIFY / DONE）
- PM：只能执行 WONT_DO（关闭）

前端同步改为按目标状态过滤按钮可见性：

```js
function canTransitTo(status) {
  if (userStore.role === 'DEV') return true
  if (userStore.role === 'PM') return status === 'WONT_DO'
  return false
}
```

> **答辩价值**：这条缺陷很好地说明了
> 「`@PreAuthorize` 是粗筛，Service 内部分支是细判」
> 两层必须**协同**而不是各自为政。
> 注解写窄了，Service 里写得再对也没用。

---

### 缺陷 4：ADMIN 代操作任务后，任务被永久卡死

**现象**：原代码在"未指派任务被首次领取时自动认领"处，**无条件**
把当前操作人设为负责人：

```java
if (task.getAssigneeId() == null) {
    update.setAssigneeId(UserContext.getUserId());   // ← ADMIN 也会被设成负责人
}
```

但 ADMIN 也能流转任务，且 ADMIN **不是 DEV 角色**。
于是一旦 ADMIN 操作了一个未指派任务：
1. 负责人被设成 ADMIN；
2. 此后任何 DEV 来推进状态，都会在数据归属校验处被拒
   （"该任务已指派给他人，你无权操作"）；
3. 任务彻底卡死，且没有 DEV 能接手。

**修复**：仅当操作人是 DEV 时才自动认领；
ADMIN 属于运维/代操作视角，不应改变任务的归属关系：

```java
if (task.getAssigneeId() == null
        && RoleEnum.DEV.getCode().equals(UserContext.getRole())) {
    update.setAssigneeId(UserContext.getUserId());
}
```

## 五、边界测试

> 目标：极端取值下系统行为**可控**，不会出现超时、截断丢数据等情况。

| # | 用例 | 预期 | 实测 |
|---|------|------|------|
| B1 | 反馈内容 5000 字（超 2000 上限） | 明确拒绝 | ✅ 400 拒绝 |
| B2 | 反馈内容恰好 2000 字 | 通过 | ✅ 200 |
| B3 | 创建问题时不关联任何反馈 | 成功 | ✅ 200 |
| B4 | 回查确认关联反馈数为 0 | 0 条 | ✅ 0 条 |
| B5 | 批量导入 201 条 | 拒绝（200 上限） | ✅ 400 |
| B6 | 批量导入 200 条 | 成功 + 耗时可控 | ✅ 200，0.28s，数据库确认 200 条 |

**关于 B1 的设计取舍**：超长文本选择**明确报错**而不是自动截断。
理由是反馈原文属于证据材料，静默截断会让用户误以为完整录入了，
事后无法追溯丢失了什么。宁可报错让用户自己删减。

**关于 B6 的性能**：200 条批量导入耗时 0.28s，
因为整个批次在单个事务内执行，且未触发 N+1 查询，性能可接受。

**结论**：6 / 6 通过。

## 六、并发测试

> 目标：两人同时操作同一条数据时，**只有一个能成功**，另一个必须得到明确提示。

测试方式：用 `threading.Barrier(2)` 让两个线程对齐后同时发起请求，
模拟"两个人同时点确认/同时推进状态"的真实场景。

| # | 用例 | 预期 | 实测 |
|---|------|------|------|
| C1 | 两个 PM 会话同时确认同一张候选卡片 | 一个 200，一个 409 | ✅ [200, 409] |
| C2 | 两个 DEV 会话同时推进同一任务状态 | 一个 200，一个 409 | ✅ [200, 409] |

**实现原理**：`issue` / `improvement_task` / `ai_candidate_issue` 三张表
都带 `version` 字段并标注 `@Version`。
MyBatis-Plus 执行 UPDATE 时会自动带上 `WHERE version = ?`，
更新行数为 0 即说明数据已被他人修改，此时抛 409 Conflict。

**为什么返回 409 而不是 500**：全局异常处理把乐观锁冲突映射为 409，
前端可直接识别并提示"数据已被他人修改，请刷新后重试"，
而不是笼统的"服务器错误"。

**结论**：2 / 2 通过。

## 七、越权测试

> 目标：绕过页面**直接调接口**，权限约束必须依然生效。

这是本项目权限设计的验证重点。设计原则是：
**`@PreAuthorize` 做角色粗筛，Service 内部做数据归属细判**，两层都不能少。

| # | 用例 | 权限规则 | 实测 |
|---|------|----------|------|
| D1 | 客服调「创建任务」接口 | R1：仅 PM | ✅ 403 |
| D2 | 开发调「修改优先级」接口 | R1：优先级由 PM 定 | ✅ 403 |
| D3 | 开发调「创建任务」接口 | R1：仅 PM | ✅ 403 |
| D4 | 客服调「确认候选卡片」接口 | R1：仅 PM | ✅ 403 |
| D5 | 客服调「变更反馈状态」接口 | R1：仅 PM/ADMIN | ✅ 403 |
| D6 | 客服调「AI 运行状态」接口 | 仅 ADMIN | ✅ 403 |
| D7 | 产品经理调「AI 运行状态」接口 | 仅 ADMIN | ✅ 403 |
| D8 | 未携带 Token 访问受保护接口 | 需认证 | ✅ 401 |
| D9 | 伪造 Token | 需合法签名 | ✅ 401 |

**关于"客服不能改他人录入的反馈"**：原始反馈在本项目中**不可修改**
（没有提供更新正文的接口），这是"原始反馈只读"这条红线的直接体现。
反馈的状态变更则限定 PM/ADMIN，客服无论是否是录入人都无权操作。

**结论**：9 / 9 通过。

## 八、AI 降级专项验证

> 这是本项目的**核心差异化验证点**：证明"AI 挂了，业务不断"。

### 8.1 三种故障场景全覆盖

| 故障类型 | 模拟方式 | 走哪条分支 | 验证结果 |
|---------|---------|-----------|---------|
| 服务不可用 | `AI_SIMULATE_FAILURE=true` 开关 | 请求失败 → 降级 | ✅ provider=RULE，fallback=true |
| 请求超时 | `AI_TIMEOUT_MS` 调极小值 | `HttpTimeoutException` → 降级 | ✅ 日志 status=TIMEOUT，耗时 30000ms |
| **返回垃圾数据** | mock 服务返回非 JSON 内容 | **解析失败 → 降级** | ✅ 见下方详述 |

### 8.2 「AI 返回垃圾数据」的验证过程

这一步最容易被忽略：项目自带的"模拟故障"开关只模拟了
「服务连不上」，而**「服务能连通、返回 200，但内容不是约定好的 JSON」
是完全不同的故障**，它走的是**解析失败**分支，而不是请求失败分支。
两条分支的兜底逻辑不同，必须分别验证。

为此编写了 `scripts/mock_ai_server.py` 模拟一个"不听话"的大模型端点，
故意返回自然语言而不是 JSON，然后把后端指向它：

```bash
AI_PROVIDER=llm \
AI_BASE_URL=http://127.0.0.1:8099/garbage \
AI_API_KEY=mock-key \
bash run.sh
```

**实测结果**：

```
[status]   actualProvider = LLM      ← 配置确实生效，走的是大模型路径
[generate] HTTP 200                   ← 业务没有中断
           fallback = True            ← 已降级
           provider = RULE            ← 实际由规则实现产出
           message  = AI 服务不可用，已自动降级为本地规则实现；以下结果由规则生成，请逐张确认。
           cards    = 9               ← 正常产出 9 张候选卡片
```

**落库的证据**（`ai_generation_log` 表）：

```
id=5  biz_type=CLUSTER  provider=RULE  status=FALLBACK  cost_ms=69
      error_msg = AI 返回内容无法解析为 JSON：好的，我已了解您的问题。关于报销软件...
```

这里有几个关键点：
1. `provider` 记的是 **RULE**（实际生效的实现），不是配置值 LLM
   —— 记录的是事实而非意图；
2. `status=FALLBACK` 与 `error_msg` 一并落库，事后可完整复盘
   「当时到底出了什么事、系统是怎么应对的」；
3. 整个过程中用户侧只看到一次正常的结果返回，
   感知不到中间失败过。

### 8.3 四种日志状态均已实测出现

| 状态 | 含义 | 是否实测出现 |
|------|------|-------------|
| `SUCCESS` | 调用成功 | ✅ |
| `FAILED` | 调用失败（如 Key 失效） | ✅ |
| `TIMEOUT` | 调用超时 | ✅ |
| `FALLBACK` | 已降级为规则实现 | ✅ |

### 9.3 已知限制（诚实交代，不属于缺陷）

1. **规则实现的语义理解有限**：只能识别预设关键词与句式，
   对全新表述、反讽、隐含诉求无能为力。详见 `docs/06-ai-design.md` 的局限说明。
2. **聚类不跨模块**：这是**有意为之**的硬约束 ——
   跨模块合并会让责任人和验收标准变得模糊，宁可多几张卡片让人判断。
3. **单机部署**：当前为本机 Windows + Nginx 方案，未做负载均衡与水平扩展。
4. **图片存本地磁盘**：默认不启用 OSS，演示环境下更稳；
   生产环境可通过一行配置切换到 OSS 实现。
5. **无自动化测试框架集成**：测试脚本为独立 Python 脚本，
   未接入 CI；每次跑完需手动执行 `scripts/reset_demo_data.sh` 恢复数据。
