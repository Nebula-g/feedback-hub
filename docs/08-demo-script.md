# 演示脚本（9 步）

> 用途：答辩现场按本脚本逐步操作，确保 8 条验收场景**逐条被覆盖**。
> 前置：已执行 `bash scripts/reset_demo_data.sh`，后端 8081、前端 5173（或 Nginx 8080）均在运行。
> 总时长建议控制在 12–15 分钟。

---

## 演示前准备

### 数据基线（确认干净）

```sql
SELECT
    (SELECT COUNT(*) FROM feedback)              AS '反馈',
    (SELECT COUNT(*) FROM feedback WHERE status='NEW') AS '待归类',
    (SELECT COUNT(*) FROM issue)                 AS '问题',
    (SELECT COUNT(*) FROM improvement_task)      AS '任务',
    (SELECT COUNT(*) FROM ai_candidate_issue)    AS '候选卡片';
```

预期：`60 / 58 / 3 / 4 / 0`

### 浏览器开两个窗口（或用一个窗口的隐私模式）

- 窗口 A：登录 `pm01`
- 窗口 B：登录 `dev01`
- 需要演示权限时再开窗口 C 登录 `cs01`

---

## 第 1 步｜30 秒：说清项目在解决什么

**操作**：打开首页，停在反馈列表。

**说辞**：

> 这套系统给报销软件公司内部用。
> 核心矛盾是：每周几十上百条反馈，**说法千差万别，但指向的问题往往重复**。
> 靠人肉看、凭印象归并，要么漏掉真问题，要么被催得最急的客户带偏。
>
> 我的做法是把链路固化成
> 「客服录入 → AI 整理 → PM 确认 → 开发跟进 → 闭环可追溯」，
> 并且有一条硬约束：**AI 只做客观整理，不给结论、不定优先级，决策权在人手里。**

---

## 第 2 步｜1 分钟：客服录入，展示只读保护

**操作**（切到窗口 C，`cs01`）：

1. 反馈录入 → 填一条：**「发票上传一直转圈，最后提示超时，报账赶不上」**
2. 模块选「发票上传」，来源选「工单」
3. 提交

**要指出的两点**：

- 录入后**找不到任何"编辑原文"的入口** —— 原始反馈只读，这是设计约束不是功能缺失；
- 用 `cs01` 打开「新建任务」或「AI 候选」页面，按钮不可见（第 9 步会用接口再验一次）。

---

## 第 3 步｜2 分钟：AI 聚类（验收场景 1）

**操作**（窗口 A，`pm01`）：

1. 进入「AI 候选工作台」
2. 模块选「发票上传」→ 点「生成候选问题」

**预期结果**：

- 多条不同表述（"上传失败""传不上去""一直转圈"…）**合并成 1 张卡片**
- 卡片上能看到**关联的反馈编号列表**
- 置信度较高（约 0.95）

**数据证据**：

```sql
SELECT id, title, ai_confidence, ai_reason
FROM ai_candidate_issue
ORDER BY id DESC LIMIT 5;
```

**要点**：卡片保留的是**原文**，不是 AI 改写后的摘要 ——
PM 点开任一条都能看到用户原话。

---

## 第 4 步｜1.5 分钟：一条反馈拆成两个问题（验收场景 2）

**操作**：确保 FB20261022-0008 处于待归类，生成候选。

反馈原文：

> 「上传发票总是失败，而且报销单被退回后也找不到原因」

**预期结果**：生成 **2 张卡片**，分别属于不同模块：

| 卡片 | 模块 | 现象 |
|---|---|---|
| 1 | 发票上传 | 上传失败 |
| 2 | 退回修改 | 看不到退回原因 |

**数据证据**（同一个 feedback_id 出现在两条关联中）：

```sql
SELECT f.feedback_no, i.title, i.module
FROM feedback_issue_link l
JOIN feedback f ON f.id = l.feedback_id
JOIN issue     i ON i.id = l.issue_id
WHERE f.feedback_no = 'FB20261022-0008';
```

**要点**：这是"并列连词切分"的效果。
刻意**不按逗号切分** —— 用户写「上传发票失败，提示文件过大」时，
逗号前后是同一件事，按逗号切会切碎。

---

## 第 5 步｜1.5 分钟：关键词相似但不合并（验收场景 3）

**操作**：针对下面两条反馈生成候选。

| 编号 | 原文 |
|---|---|
| FB20261023-0009 | 发票传不上去 |
| FB20261023-0010 | 上传显示成功但查不到 |

**预期结果**：生成 **2 张独立卡片，不合并**。

**说辞**：

> 两条都含"上传"，但一条是**传不上去**，一条是**传上去了查不到** ——
> 现象不同，修法也不同。
> 系统宁可多出一张卡片让人判断，也不替人做这个合并决定。

---

## 第 6 步｜1 分钟：依据不足时如实标注（边界）

**操作**：对下面这类反馈生成候选。

- FB20261024-0058：「有问题，找你们技术」

**预期结果**：

- 置信度**很低**（约 0.25）
- 现象里**明确标注依据不足**，而不是编一段听起来像回事的描述

**说辞**：

> 这条的关键词能匹配到"发票"，但整句话其实没说清是什么问题。
> 系统的处理是**如实标注"依据不足"并给低置信度**，
> 而不是像模像样地编一段描述 —— 后者比不做更危险。

---

## 第 7 步｜2 分钟：PM 决策 —— 修改 / 确认 / 合并 / 驳回（验收场景 4、5）

**操作**（窗口 A）：依次演示四种动作。

| 动作 | 操作 | 结果字段 |
|---|---|---|
| **修改后确认** | 改标题/描述 → 确认 | `status=MODIFIED` |
| **直接确认** | 不改 → 确认 | `status=CONFIRMED` |
| **合并** | 选已有问题 → 合并 | `status=MERGED` |
| **驳回** | 填理由 → 驳回 | `status=REJECTED`，反馈回到 `NEW` |

**重点展示**：确认后打开生成的问题详情页，看「需求说明对照」：

- `AI 草稿内容（原样保留）`
- `最终内容（PM 确认）`

**说辞**：

> 这两栏是分开存的。如果 PM 一个字没改，系统标记为"直接确认"；
> 改过，就标记为"修改后确认"。
> 这样三个月后回看，能说清**哪些是 AI 的产出、哪些是人的判断**。

> ⚠️ 这里有个坑我在 Review 时踩过：
> 一开始后端拿"现象字段"当比较基准，但前端弹窗展示的是拼装后的文本，
> 结果 PM 一字未改也被判成"已修改"。
> 后来两边统一了拼装规则才修好 —— 这种问题不实测根本发现不了。

## 第 8 步｜1.5 分钟：开发跟进与时间线（验收场景 6）

**操作**（窗口 B，`dev01`）：

1. 打开任务详情
2. 依次推进：`待开发 → 开发中 → 待验证 → 已完成`
3. 演示"验证不通过打回"（必须填原因）

**要当场演示的校验**：

| 操作 | 预期 |
|---|---|
| `TODO → DONE`（跳步） | ❌ 409 拒绝 |
| `PENDING_VERIFY → IN_PROGRESS` 不填原因 | ❌ 400 拒绝 |
| `dev01` 定优先级 | ❌ 403 拒绝 |

**数据证据**（时间线完整可追溯）：

```sql
SELECT e.id, e.from_status, e.to_status,
       u.display_name AS '操作人', e.remark, e.create_time
FROM task_event e
LEFT JOIN sys_user u ON u.id = e.operator_id
ORDER BY e.create_time;
```

## 第 9 步｜2 分钟：AI 故障降级 + 越权拦截（验收场景 7、8）

### 9.1 降级演示

**操作**：

1. 停掉当前后端
2. 以故障模式启动：

```bash
AI_SIMULATE_FAILURE=true bash backend/run.sh
```

3. 重新进入「AI 候选工作台」→ 生成候选

**预期结果**：

- ✅ 页面**正常返回卡片**（不是报错页面）
- 提示文案：`AI 服务不可用，已自动降级为本地规则实现；以下结果由规则生成，请逐张确认。`
- 接口返回 `fallback=true`、`provider=RULE`

**数据证据**：

```sql
SELECT id, biz_type, provider, status, cost_ms, LEFT(error_msg, 80)
FROM ai_generation_log
WHERE status = 'FALLBACK'
ORDER BY id DESC;
```

**说辞**：

> 关键在于三点：
> 第一，**业务没断** —— 用户侧看到的是正常结果；
> 第二，**如实告知** —— 页面明确说这是规则生成的，不冒充大模型；
> 第三，**全程留证** —— 日志里记了失败原因和最终实际用的实现。
>
> 日志里 `provider` 记的是 **RULE**（实际生效的实现），
> 不是配置值 LLM —— 记事实，不记意图。

**可选的进阶演示**（如果时间允许）：

用 mock 服务演示「AI 返回垃圾数据」这种**不同于服务不可用**的故障：

```bash
python scripts/mock_ai_server.py 8099

# 另开终端
AI_PROVIDER=llm AI_BASE_URL=http://127.0.0.1:8099/garbage \
AI_API_KEY=mock-key bash backend/run.sh
```

这条走的是**解析失败**分支，日志会记录
`AI 返回内容无法解析为 JSON：...`。

> 这一步的价值在于：项目自带的故障开关只模拟了"服务连不上"，
> 而"服务能连通但返回格式不对"是另一条分支，必须单独验证。

### 9.2 越权演示（用接口工具，绕过页面）

| 账号 | 接口 | 预期 |
|---|---|---|
| `cs01` | `POST /api/tasks` | 403 |
| `dev01` | `PUT /api/tasks/1/priority` | 403 |
| `cs01` | `POST /api/ai/candidates/1/confirm` | 403 |
| `cs01` | `PUT /api/feedbacks/1/status` | 403 |
| 无 Token | `GET /api/feedbacks` | 401 |

**说辞**：

> 权限我做的是两层：
> 注解层做**角色粗筛**，Service 内部做**数据归属细判**。
> 只靠注解拦不住"同角色但拿到别人的数据"这种情况，
> 所以两层都必须有。

**演示结束后**：恢复正常模式
```bash
bash backend/run.sh
bash scripts/reset_demo_data.sh
```

## 演示注意事项

1. **先重置数据**：演示前务必执行 `reset_demo_data.sh`，
   否则可能看到上一轮遗留的卡片，讲不清楚。

2. **默认用规则实现演示**：`provider=rule` 断网可用，
   不会因现场网络问题翻车。想展示大模型效果时再切换。

3. **降级演示放最后**：因为要重启后端。
   演示完记得切回正常模式并重置数据。

4. **权限演示用接口工具**：在页面上角色按钮本来就不可见，
   用 Postman/curl 直接调接口才能证明"绕过页面也拦得住"。

5. **每个结论都要指数据**：说到"系统标记了是否已修改"，
   就把问题详情页的对照栏指出来；
   说到"留证"，就把 `ai_generation_log` 的表打开。
